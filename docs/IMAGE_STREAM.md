# 静态图片串流：格式协商与有界流水线

图片串流继续作为 WebRTC 的兼容回退。当前支持完整 JPEG 与有损 WebP，不增加帧间依赖。
源帧发布仍最多约 15 fps（66 ms 间隔），此次改动不改变该上限或 WebRTC 的恢复策略。

## 格式协商

新网页使用 `media=2&images=3` 连接。新服务端升级到图片协议 v3；旧服务端仍识别
`media=2`，继续提供 v2 JPEG。旧网页连接新服务端时保持原始 JPEG / v2 协议和单帧窗口。

网页实际解码内嵌的 2×2 有损 WebP 样本，校验尺寸；错误、API 不可用或 1500 ms 内未完成，
均保持 JPEG。探测不依赖 User-Agent、Canvas、WebCodecs 或 HTTPS；成功后发送
`{"type":"image-format","format":"webp"}`。配对和连接无需等待探测完成。

「设置 → 画面与串流」可选择 JPEG / WebP，并输入 1–100 的图片质量，默认 WebP、75。
选择 JPEG 时始终编码 JPEG；选择 WebP 时仍必须通过浏览器能力协商，旧客户端、不支持或
已回退的浏览器继续使用 JPEG。设置保存到 App，重启后保留，取消输入不改变设置；非法
质量输入被拒绝，未知格式或超出范围的已存质量使用默认值。

Android 使用 Bitmap 的有损 WebP 编码（Android 30 前使用 WEBP 枚举）。用户质量值同时
用于 JPEG 和 WebP，包括 WebP 失败后的 JPEG 回退；不同编码器的相同数值不表示相同视觉质量。
格式 / 质量保存后应用到后续图片，无需重连手机或浏览器；现有 200 ms 源检查在静态画面上
也触发重新编码。每次编码只读取一份不可变设置，避免质量在编码与报告之间变化。已经
在传输或解码的旧图片可能先完成。设置不影响 H.264 / HEVC 直通的视频质量。

压缩暂存区复用，
发布的字节数组保持不可变。WebP 返回失败或抛出异常时丢弃部分输出，改用 JPEG，当前
视频输出生命周期内不再调用失败的 WebP 编码器。

浏览器运行中遇到 WebP 解码错误，会 ACK 失败图片并请求 `image-format: jpeg`，保留已有
画面；服务端在本连接内锁定 JPEG，重连后可重新探测。没有成功提交过画面时继续等待。
服务端不会向尚未声明支持 WebP 的客户端发送缓存的 WebP。格式变化通过现有 200 ms 源
检查触发静态纹理重新编码，因此不依赖手机再产生一帧。

目前不采用 AVIF、JPEG XL、动画图片或差分区域协议。WebP 的带宽收益与 Android 编码
成本需要真机测量，支持解码不保证编码更快或端到端延迟更低。

## 帧布局与确认

v3 的前 36 字节沿用 [v2](MEDIA_PRESENTATION.md) 的字段位置，但 magic 为
`0x33565057`（WPV3）；偏移 36 是 little-endian uint32 格式编号，1 为 JPEG，2 为 WebP。
偏移 40 起为完整图片。客户端拒绝未知格式或截断的包。

每张 v3 图片通过以下消息单独确认，包括解码失败、被更新帧淘汰、媒体版本过期和 RTC
接管后放弃的图片：

```json
{"type":"ack","sessionId":7,"videoEpoch":42,"sequence":99}
```

服务端只释放三个字段完全匹配的在途帧；重复、过期或无编号的 ACK 不能释放 v3 槽位。
ACK 不是累计确认。客户端拥塞队列保存每个不同 ACK，不能把两个不同图片的确认合并。
旧协议继续使用无编号 ACK。WebRTC 的 `rtc-ready` 也不能代替 v3 图片确认。

## 缓冲与低延迟

- 服务端默认最多两张图片在途，不建立逐帧发送队列，空位出现时只读取最新源帧。
- 在途图片 payload 总量限制为 2 MiB；超过预算的单张图片可以独占窗口，避免高分辨率
  静态画面永远无法发送。已写入 TCP 的旧数据无法撤回。
- 最早在途帧等待达到 250 ms 时，窗口收缩为一帧；ACK 耗时达到 250 ms 后维持单帧至少
  一秒，随后在有发布或 ACK 事件时重新评估。它主要限制积压，不能消除网络本身的延迟。
- 浏览器使用三个 img：一个显示、最多两个加载 / 解码。加载中的图片不会清空已显示图片。
  较新图片先完成时提交新图并取消旧任务；旧回调不能覆盖新图，也不能重复 ACK。
- 媒体版本变化、重连或 RTC 首帧接管时，取消待解码任务。画面与触控尺寸始终一起提交。
- 图片在途超时、音频背压、控制消息优先级与 WebSocket 断连规则保持原有约束。

三张 1280×720 RGBA 解码图片约占 10.5 MiB，另有压缩数据和浏览器内部开销；这是有界
并行解码，需要与车机内存、解码性能一起评估。它不会绕过 Android 的 15 fps 发布限制。

`window.wheelplayStats.image` 提供协议、实际最近图片格式、窗口、在途帧数、payload
字节数、实际编码质量及最近 ACK 耗时。ACK 耗时包含传输、浏览器解码 / 淘汰和确认回程，不等于纯 RTT
或显示器已经扫描输出的时间。

## 验证

- 网页单测覆盖能力探测、v2 / v3 包头、双解码、乱序完成、资源释放、逐帧 ACK、WebP
  回退、重连与 RTC 接管隔离。
- Android 单测覆盖编码失败回退、发布字节不可变、双帧与字节预算、慢 ACK 降窗、精确
  确认以及真实 WebSocket 格式协商。设置测试覆盖实际 Compose 操作、持久化、输入校验、
  用户格式优先级及回退时的质量参数。旧协议的单帧背压测试继续保留。
- `npm run test:browser:media` 使用真实 Chromium / WebSocket 解码 JPEG、WebP，注入
  损坏 WebP 检查 JPEG 回退，并验证缩放补偿下的触控、重建、旋转与重连。
- `WebRuntimeTest.staticFrameIsReencodedWhenImageFormatOrQualityChanges` 是设备测试：
  验证真实 EGL 纹理在没有后续源帧时切换格式 / 质量并能解码；仅编译该测试不等于完成真机验证。

设备回归应比较相近文字清晰度下的流量、CPU、帧龄及触控到画面的延迟，并覆盖动态地图、
菜单和静态屏幕。自动化测试验证协议与行为，不提供真实设备上的性能提升百分比。
